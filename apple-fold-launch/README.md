# 折りたたみ iPhone 初回予約 — 準備手順とオペレーション

初回の予約争奪戦を**手動で、最速で**通すための準備書と当日用ボード。
自動購入（カート投入から決済送信までの無人自動化）は含まない。理由は「なぜ自動購入ボットを作らないか」に書いた。

## 中身

| ファイル | 用途 |
|---|---|
| `index.html` | 当日用オペレーションボード。カウントダウン／時刻同期／準備チェックリスト／当日ランブック。依存ライブラリなし |
| `README.md` | この準備手順書 |

## 使い方

```sh
# 通知APIを使うならローカルサーバ経由で開く（file:// だと通知がブロックされる環境が多い）
cd apple-fold-launch
python3 -m http.server 8080
# → http://localhost:8080/
```

`index.html` をダブルクリックして直接開いても、カウントダウン・音・画面フラッシュは動く。ブラウザ通知だけが環境によって塞がれる。

状態は `localStorage` にのみ保存される。**当日使うブラウザ・プロファイルで開いて準備すること。**別のブラウザで開くとチェックは引き継がれない。

## 時刻同期について

争奪戦で端末の時計が数十秒ずれていると、それだけで負ける。

1. ページを開くと自動で外部の時刻APIに同期を試みる（Cloudflare → worldtimeapi → timeapi.io の順にフォールバック）
2. **同期は失敗する可能性がある**（CORS、ネットワーク制限、APIの障害）。バッジが「同期失敗」なら手動オフセットを使う
3. 手動オフセット：正確な時計（[JST Clock](https://www.nict.go.jp/JST/JST5.html) など）と見比べ、PCが進んでいる分を**負値**、遅れている分を**正値**で ms 入力して「適用」

作者環境では外部APIへの到達が遮断されていて自動同期の実地検証ができていない。**当日までに必ず一度、手元で同期が通るか確認すること。** 通らなければ手動オフセット運用に切り替える。

# 準備手順

チェックリストの各項目は `index.html` にも入っている。ここは背景の説明。

## 今すぐやる（数日かかるもの）

### 1. カードの利用可能枠を確認する ← 最優先
本体価格は40万円前後と予想されている。**枠不足による決済失敗は、争奪戦の最も現実的な敗因**。他の予約や引き落としと重なると簡単に足りなくなる。
一時増枠はカード会社の審査に**数日**かかる。今日申請する。

### 2. 3Dセキュア（本人認証）の登録を確認する
未登録・パスワード失念だと、決済直前で認証画面に飛ばされて詰む。

### 3. 予備のカードをもう1枚 Apple Account に登録する
1枚目が弾かれてからカード番号を打ち直す時間はない。

### 4. 配送先住所を「実際に注文画面まで進んで」検証する
登録しただけでは不十分。番地の全角半角、建物名の長さでバリデーションに落ちることがある。安い小物を一度カートに入れて、決済ボタンの直前まで進んで確認する（そこで中止すればよい）。

## 構成を決め切る（当日の迷いをゼロにする）

当日に考える項目が1つでも残っていると、そこで数十秒溶ける。**紙に書いて画面の横に置く。**

- **容量・色の第1〜第3希望**：第1希望が消えた瞬間に迷うと第2希望も消える
- **SIMフリー（Apple直販）かキャリアか**：導線が完全に別。当日比較は不可能
- **下取り（Trade In）を使うか** → 初回は**使わない方が速い**。手順が増える。下取り価格は後から個別に売る方が高いことも多い
- **AppleCare+ を当日付けるか** → 購入後の猶予期間内なら後から加入できる。速度優先なら当日は付けない
- **配送か店舗受取か**：在庫枠が別管理。店舗受取の方が早く手に入る場合がある

## 前日までに（環境）

- 回線を2系統（固定回線＋モバイル）確保して切替できるようにする
- **PCとスマホの2デバイスで待機**。Web と Apple Store アプリで別導線
- 購入に使うブラウザの**拡張機能をOFF**。広告ブロッカーやスクリプト遮断系が決済フレームを壊すことがある
- 全デバイスを電源に接続
- Apple Store アプリを最新版に更新し、通知をON
- このボードで時刻同期

## 保険を張る — ここが一番効く

**争奪戦の勝率は「1導線の速度」より「導線の本数」で決まる。**

- キャリア（docomo / au / SoftBank）と量販店の予約も同時に走らせる
- 家族に1導線ずつ割り当てる。1人で3画面を捌くより、3人で1画面ずつの方が速い
- ただし**各チャネルのキャンセル可否を事前に確認**しておく。本命が取れたら速やかに降りる

## 当日

`index.html` のランブックを上から潰す。要点だけ再掲：

- **リロードは1回ずつ**。F5連打・多重タブは bot 判定を招く。締め出される損失の方が大きい
- 開始5分前に1回リロードしてセッション切れを防ぐ
- 注文完了したら注文番号をスクリーンショット
- 本命確保後、他チャネルを速やかにキャンセル

# なぜ自動購入ボットを作らないか

倫理論ではなく、**目的に対して手段が不利**だから。

### 1. Apple の予約は「秒殺型」ではなく「配送日後ろ倒し型」
GPU やスニーカーのドロップとは挙動が違う。在庫が瞬時にゼロになるのではなく、注文が進むほど出荷予定日が後ろにずれる。ボットが稼ぐ数十秒で変わるのは主に「いつ届くか」であって「買えるか」ではない。初代折りたたみは供給が絞られる想定なので差は広がるが、それでも**導線の本数を増やす方が効く**。

### 2. 一発勝負とボットは最悪の相性
Apple Store は Akamai の bot 検知下にある。素朴な Playwright / Selenium 自動化はチャレンジ挿入やセッション破棄の対象。加えて 3Dセキュア、キャリア回線契約、下取り選択など**人間の介在が要る分岐が決済直前に入る**。

繰り返し使わない＝**本番でデバッグする機会がゼロ**。ボットが想定外の画面で固まった瞬間、手動なら買えていた枠を失う。リスクの方向が非対称。

### 3. 規約リスク
Apple の利用規約は自動化手段による注文を禁じている。検知された場合は注文キャンセル、最悪 Apple Account の制限。**通った注文が後から消えるのが一番痛い結末。**

### 結論
自動化すべきなのは「決済の送信」ではなく「**その前段の準備と、当日の意思決定の排除**」。このボードはそれをやる。
